# Инструкция: как создать шаблон языка для редактора

Эта инструкция — практическое руководство для написания нового файла
`templates/*.json` (или правки существующего) с учётом всех особенностей
кодогенерации (`src/utils/CodeGenerator.ts`) и дизассемблирования
(`src/utils/Disassembler.ts`). Общее устройство проекта — в корневом
`README.md`; здесь — именно "как написать команду, чтобы она не сломалась".

Формальная схема файла — `src/utils/TemplateSchema.ts` (`RawTemplate`,
`TemplateCommand`, `TemplateField`). Валидатор — `npm run drake:check`
(`tools/validate-drake-template.mjs`) — **запускайте его после каждой правки**,
но держите в голове: он ловит не всё (см. раздел "Чего валидатор НЕ проверяет").

---

## 1. Два режима — выбираются один раз на весь язык

| | Байт-режим (`opcode`+`length`) | Легаси-режим (`template`-строка) |
|---|---|---|
| Для чего | VM/байт-код языки (DrakeScript) | текстовые языки (C, ASM) |
| Импорт/дизассемблирование | ✅ поддерживается | ❌ принципиально нет (`canDisassemble`) |
| `type` поля | байтовый (`uint8`, `reg`, ...) → переводится в UI-тип через `typeMap` | уже готовый UI-тип (`string`/`number`/`boolean`) |
| Адресация переходов | `role: "address"` поле + `of` | `weight` + `{portId:address}`-подстановка в printf-строке |

**Не смешивайте режимы внутри одного языка.** `canDisassemble(template)`
включает импорт для всего файла, если хотя бы одна команда байт-режимная —
но `Disassembler` понимает только байт-режимные команды. Если в "байтовом"
языке случайно окажется легаси-команда (`template` вместо `opcode`), она
никогда не будет найдена при разборе потока байт и приведёт к "неизвестный
opcode" в месте, где она реально встретилась в выводе. `drake:check`
предупредит, если на одной команде заданы оба поля сразу, но не проверяет
смешение в масштабе всего файла — это на вас.

Эта инструкция в основном про **байт-режим** (он сложнее и именно под него
заточен дизассемблер); для легаси-режима — см. раздел 7.

## 2. Верхний уровень файла

```json
{
  "id": "DrakeScript",
  "name": "script for Pixel (.drk)",
  "extension": "drk",
  "useHex": true,
  "boilerplate": { "start": "", "end": "" },
  "typeSizes": { "uint8": 1, "uint16": 2, "int32": 4, "reg": 1, "enum": 1, "can_id": 2 },
  "typeMap":   { "uint8": "number", "uint16": "number", "int32": "number", "reg": "register", "enum": "number", "can_id": "number" },
  "dataTypes": [ ... ],
  "nodeGroups": [ ... ],
  "commands": { "cmd_Xxx": { ... } }
}
```

- **`typeSizes`** — байтовый размер каждого `field.type` (в байтах). Используется
  и генератором (`compileEmission`), и дизассемблером (`readUint`) — **должны
  совпадать всегда**, это буквально один и тот же словарь для записи и чтения.
  Тип, которого нет в `typeSizes`, молча считается 1-байтным
  (`typeSizes[f.type] ?? 1`) — `drake:check` выдаст об этом `warn`, но не
  остановит сборку. Не полагайтесь на дефолт, заводите тип явно.
- **`typeMap`** — переводит байтовый `type` поля в UI-тип порта (для
  совместимости связей и для подбора `dataTypes` по имени). Если типа нет в
  `typeMap`, как UI-тип используется сырой `field.type` напрямую — это ОК,
  только тогда заведите `dataTypes[]` с `name`, который **точно совпадает**
  с этим сырым именем, иначе выпадающий список/подсветка при импорте не
  сработают.
- **`dataTypes`** — определяют цвет порта и (опционально) `options[]`
  (выпадающий список). `options[].value` обязан быть в hex-виде
  `0xNN` **ровно в том формате**, в котором дизассемблер печатает байт
  (`'0x' + raw.toString(16).toUpperCase().padStart(2,'0')`, т.е. заглавные
  буквы, минимум 2 цифры) — иначе сравнение в `formatFieldValue`
  (`Disassembler.ts`) не найдёт совпадение, и после импорта в поле будет сырой
  hex вместо подписи. Реальный баг, который только что встретился и исправлен
  в `drake_template.json`: `{"value": "0xs00", "label": "FALSE"}` — опечатка
  ломала подстановку `FALSE` при каждом импорте. Проверяйте `options[].value`
  глазами, валидатор это не ловит.
- **`useHex`** — глобальный дефолт для `:hexN` в кодогене (не трогает
  `role: "address"`-токены и явный `:dec`, см. раздел 4).
- **`boilerplate.start`/`.end`** — текст до/после сгенерированного кода.
  **Не пишите туда строки, целиком состоящие из `0xNN`-токенов** — дизассемблер
  вычленяет байт-поток именно по этому признаку (`extractByteStream`,
  `Disassembler.ts`), и ложно опознает такую строку как часть байт-кода.

## 3. Команда (`TemplateCommand`)

```json
"cmd_IfRegValGeq": {
    "name": "If (Reg >= Val)",
    "nodeType": "function",
    "visual": { "color": "#f59e0b" },
    "control": { "in": "exec_in", "out": { "true": "exec_true", "false": "exec_false" } },
    "fields": [
        { "name": "Register", "type": "reg",    "dir": "in", "portId": "op1" },
        { "name": "Value",    "type": "int32",  "dir": "in", "portId": "op2" },
        { "name": "jump",     "type": "uint16", "role": "address", "of": "exec_false" }
    ],
    "opcode": "0x1A",
    "length": 8
}
```

- **`name`** — подпись в палитре/на ноде.
- **`nodeType`** — свободная строка. На деле используется **только в одном
  месте**: `Disassembler.layout()` ставит команды с `nodeType: "event"` на
  предпочтительную верхнюю строку раскладки после импорта. **Не влияет на
  порядок кодогенерации** — это частая ошибка-ожидание. Для точки входа в
  код нужен конкретный `definitionId`, см. ниже.
- **`visual.color`/`.icon`** — чисто косметика.
- **`control.in`** — id входного exec-порта, либо `null`, если в ноду в
  принципе нельзя провести связь (так сделан `cmd_ScriptInit` — это точка
  входа, а не шаг потока).
- **`control.out`** — один из двух вариантов:
  - строка (`"exec_out"`) — линейное продолжение, один исход;
  - `{ "true": "...", "false": "..." }` — развилка. Подписи портов
    (Prev/Next/TRUE/FALSE) проставляются автоматически, в файле не хранятся.
- **`opcode`** — hex-строка (`"0x1A"`), **уникальная** в пределах файла.
  Валидатор НЕ проверяет уникальность (см. раздел 8) — при коллизии
  вторая команда в `Object.entries()` молча перекроет первую в
  `Disassembler.opcodeMap`, и первая станет недостижима при разборе.
- **`length`** — размер инструкции в байтах **включая опкод**. Обязан быть
  равен `1 + Σ typeSizes[field.type]` по всем полям — это проверяет
  `drake:check`. Расхождение — то же самое, что сдвиг всех адресов после
  этой команды (исторический баг с `SetScriptArgReg32`, см. README).

## 4. Поле (`TemplateField`)

```ts
{ name?, type, dir?: 'in'|'out'|'inout'|'const', portId?, value?, role?: 'address', of? }
```

- **`type`** — байтовый тип (`uint8`/`uint16`/`int32`/`reg`/`enum`/`can_id`/
  свой). Сигнатура важна: **тип, начинающийся с `int`, трактуется дизассемблером
  как знаковый** (`toSigned()` в `formatFieldValue`), всё остальное — без
  знака. Называйте тип по этому правилу (`int8`/`int16`/`int32` для знаковых).
- **`dir`** (по умолчанию `"in"`, если не указан):
  - `"in"` → входной порт. В комментарии экспорта подставляется `{portId:dec}`.
  - `"out"` → выходной порт (приёмник результата, напр. `res` у `SetRegVal`).
    В комментарии — просто `{portId}`, без `:dec`. Работает и для записи
    инлайн-значения прямо на ноде (см. `Node.tsx`).
  - `"inout"` → входной порт с типом `ref:<uiType>` — "регистр читается и
    перезаписывается на месте" (`IncReg`, `AndRegVal` и т.п.).
  - `"const"` → **не становится портом вообще** (`portId` не нужен). Жёстко
    зашитое значение (`value`, по умолчанию 0), которое пишется в байты
    КАЖДЫЙ раз для этой команды. При импорте значение не сохраняется в
    данные ноды, а сверяется: не совпало — предупреждение о возможной
    рассинхронизации разбора (не останавливает импорт). Годится для
    reserved-байт/паддинга/сигнатуры варианта команды — см. `cmd_ScriptInit`
    (5 const-байт `mode`/`d1..d4`, все нулевые).
- **`portId`** — обязателен для всех полей, кроме `role:"address"` и
  `dir:"const"` (проверяется `drake:check`).
- **`role: "address"` + `of`** — поле физически занимает байты в инструкции
  (как любое другое, размер берётся из `typeSizes`), но **не рендерится как
  порт с данными** — это адрес ноды, подключённой к control-порту `of` (имя
  control-порта ЭТОЙ ЖЕ команды — `drake:check` проверяет, что оно реально
  существует в `control`). При кодогене туда подставляется адрес ноды,
  подключённой к этому control-выходу (`{of:address:hexN}`); при
  дизассемблировании — декодированный адрес разворачивается обратно в связь.
  **Это ключевой механизм для переходов** — подробно в разделе 5.

Порядок полей в массиве `fields[]` = порядок байт сразу после опкода.
**Меняя порядок/состав полей у уже используемой команды, вы ломаете обратную
совместимость со всем, что уже экспортировано этим опкодом** — версионирования
формата нет.

## 5. Переходы: `role: "address"` и почему это критично

Модель простая и единая что для кодогена, что для дизассемблера, что для
самого редактора:

- **Порт БЕЗ адресного поля** (обычный `exec_out`/`exec_true` у функций и
  "true"-ветки условий) — адрес назначения не хранится нигде явно. Он
  определяется **исключительно физическим соседством** в линейном потоке
  байт: следующая инструкция и есть то, куда "проваливается" выполнение.
- **Порт С адресным полем** (`exec_false` у условий, единственный `exec_out`
  у `cmd_Goto`) — адрес назначения **зашит прямо в байты этой инструкции**
  (`role:"address"`-поле), физическое соседство не имеет значения, можно
  ссылаться куда угодно, вперёд или назад по потоку.

Следствие для кодогена: если в графе **две или более ноды** своим
"безадресным" выходом ведут в одну и ту же ноду — физически оказаться прямо
перед ней в байтах может только одна из них (та, что раньше дошла при обходе
графа). Для остальных нужен **настоящий переход** — либо явная связь через
порт с `role:"address"`, либо отдельная Goto-подобная нода-мост.

Раньше это решалось вручную (пользователь сам тянул провод в `cmd_Goto`).
Сейчас редактор сам это ловит **на этапе соединения**: если второй exec-провод
пытается войти в уже занятый вход, а у источника нет своего адресного поля,
`useEditorStore.completeLinking` не создаёт связь напрямую, а предлагает
выпадающий список команд-мостов (`findAddressBridgeCommands` в
`TemplateSchema.ts`) — ищутся они **по структуре**, а не по имени
`cmd_Goto`: `control.in` есть, и хотя бы один из control-выходов
(`control.out`-строка либо `true`/`false`) несёт `role:"address"`.

**Практическое требование к ЛЮБОМУ байт-режимному языку с ветвлением:**
в файле обязана быть хотя бы одна такая команда (минимум — безусловный Goto:
`control.in` + одиночный `control.out` + единственное `role:"address"`-поле
на этот выход). Без неё пользователь физически не сможет соединить сходящиеся
ветки (`if/else`, которые потом "сливаются" в общий код) — соединение будет
заблокировано с сообщением об ошибке. Условные команды (`If*`) тоже подходят
как мост (используется их `false`-выход), но у них остаются незаполненными
`true`-ветка и операнды сравнения — их пользователь донастраивает сам.

Пример минимального Goto:

```json
"cmd_Goto": {
    "name": "Goto",
    "control": { "in": "exec_in", "out": "exec_out" },
    "fields": [
        { "name": "jump", "type": "uint16", "role": "address", "of": "exec_out" }
    ],
    "opcode": "0x80",
    "length": 3
}
```

⚠️ Размер типа адресного поля ограничивает адресуемое пространство без
всякой проверки переполнения: `uint16` → максимум 0xFFFF байт кода; если
скрипт больше — адрес молча обрежется по младшим байтам (`wrapHex`/`hexBytes`
берут `(v >> k*8) & 0xFF`), и переход уйдёт не туда. Берите тип с запасом под
реальный максимальный размер программы.

## 6. Точка входа, editor-only команды, нулевой маркер

- **Точка входа для кодогена** — `CodeGenerator.generate()` ищет узлы с
  `definitionId` строго `"cmd_start"` или `"cmd_ScriptInit"` (список
  захардкожен в движке, из шаблона не настраивается). Заведите ровно такую
  команду для своего языка — без неё обход начнётся с произвольного узла
  массива нод, и порядок инструкций станет недетерминированным для сложных
  графов. Можно иметь несколько экземпляров такой ноды в графе (несколько
  независимых точек входа) — обойдутся все.
- **Editor-only команды** — ни `opcode`, ни `length`, ни `template` не заданы
  (`cmd_function`, `cmd_FunctionStart`, `cmd_Begin` в DrakeScript). Нода
  существует в палитре и на канвасе, но полностью игнорируется кодогеном
  (`shouldIncludeNode` вернёт `false`) — используется для служебной разметки
  (вставка подграфа функции через `node.data.file`, см. `expandFunctions()`
  в `CodeGenerator.ts`).
- **"Немой" маркер нулевой длины** — `opcode` не задан, `length: 0`
  (`cmd_End` в DrakeScript). Не занимает байт в потоке, но получает адрес —
  удобная "точка-заглушка", на которую может вести переход, не производя
  собственной инструкции. Дизассемблер при разборе синтезирует такую ноду
  там, где адрес-цель перехода не совпадает ни с одной реальной инструкцией
  (`synthesizeMarkers`). На файл допускается **только один** такой маркер —
  берётся первый найденный (`!this.markerCommand` в конструкторе
  `Disassembler`).

  ⚠️ **Известный баг**, если решите использовать этот паттерн: если
  true-ветка условия доходит до такого маркера РАНЬШЕ, чем обработана
  отложенная false-ветка, первая нода false-ветки получает **тот же адрес**,
  что и маркер, и физически встаёт на его место в потоке байт — то есть в
  реальном бинарнике на месте "End" не будет настоящей инструкции остановки,
  выполнение молча провалится в код другой ветки. Возникает в любом
  `if/else`, где обе ветки независимо приходят к общему "немому" концу. Не
  исправлено на уровне движка — если это критично, сделайте у маркера
  реальный опкод (`halt`/`return`) вместо `length: 0`.

## 7. Легаси-режим (`template`-строка) — для текстовых языков

```json
"cmd_SetRegVal": {
    "control": { "in": "exec_in", "out": "exec_out" },
    "template": "    reg[{res}] = {op1};",
    "weight": 1
}
```

- `type` полей — уже готовый UI-тип (`string`/`number`/`boolean`), не
  байтовый.
- `weight` (по умолчанию 1) заменяет `length` — абстрактный "вес" для
  адресации (нужен только если язык вообще считает адреса/метки, см.
  `useLabels`).
- Подстановка `{portId}`/`{portId:modifier}` работает так же, как в
  байт-режиме (`processNode` в `CodeGenerator.ts` не различает режимы на
  этом этапе) — модификаторы `:hexN`/`:dec`/`:value`/`:label`/`:address`/
  `:delta` доступны и здесь.
- **Дизассемблирование принципиально недоступно** для команд этого режима
  (`canDisassemble` смотрит на `opcode`, `Disassembler` просто не умеет
  разбирать произвольный текст обратно). Если нужен импорт — это не ваш
  режим, переходите на байт-режим целиком.

## 8. Чего валидатор (`npm run drake:check`) НЕ проверяет

Проверяет (см. `tools/validate-drake-template.mjs`): арифметику `length`,
существование control-порта у `role:"address"`-полей, наличие `portId` у
обычных полей, конфликт `opcode`+`template` на одной команде, ссылки
`nodeGroups[].nodes[].commandId`.

**НЕ проверяет** (контролируйте вручную/глазами):
- Уникальность `opcode` между командами одного файла.
- Корректность `dataTypes[].options[].value` (формат `0xNN`, совпадение с
  реально кодируемыми байтами) — опечатка тут не кидает ошибку нигде, просто
  тихо не подсвечивает нужный пункт списка после импорта.
- Наличие хотя бы одной команды-моста (`role:"address"` на выходе) для
  языков с ветвлением — без неё пользователь упрётся в блокировку соединений
  в редакторе, никакой статической проверки на это нет.
- Смешение байт-режима и легаси-режима в одном файле (кроме варнинга про
  одну и ту же команду).
- Переполнение адресного поля (`uint16` и т.п.) относительно реального
  размера программ на этом языке.
- Присутствие "чисто hex" строк в `boilerplate` (сломает `extractByteStream`
  при импорте).

## 9. Пошаговый рецепт: новый язык с нуля

1. Скопируйте `drake_template.json` как отправную точку структуры (проще
   редактировать существующий валидный файл, чем писать с нуля).
2. Замените `id`/`name`/`extension`/`boilerplate`.
3. Определите `typeSizes` и `typeMap` для своих байтовых типов.
4. Заведите `dataTypes[]` — хотя бы `register`-подобный с `options[]`, если
   у языка есть именованные регистры/константы.
5. Добавьте точку входа `cmd_start` или `cmd_ScriptInit` (`control.in: null`).
6. Добавьте **минимум один** Goto-подобный мост (раздел 5) — даже если
   кажется, что переходы не понадобятся: как только в графе появится первое
   схождение двух веток, он станет обязателен.
7. Опишите остальные команды: опкод, `length` = `1 + Σ typeSizes`, поля по
   порядку байт.
8. Для условных команд — на один из `true`/`false` выходов повесьте
   `role:"address"`-поле (на второй — не вешайте, он должен быть обычным
   fallthrough).
9. `npm run drake:check` — чините ошибки/варнинги.
10. Запустите `npm run dev`, соберите тестовый граф с веткой `if/else`,
    сходящейся в общий код, через `File → Export`, затем
    `File → Import Program... (disassemble)` — граф должен восстановиться.
    Это лучшая практическая проверка, которую не заменяет валидатор.
11. При ветвлении намеренно проверьте схождение обеих веток в `cmd_End`-
    подобный маркер (если он есть) — на баг из раздела 6.

## 10. Краткий чек-лист перед коммитом нового/изменённого шаблона

- [ ] `npm run drake:check` — 0 ошибок.
- [ ] Каждый `opcode` встречается один раз во всём файле.
- [ ] Есть команда `cmd_start`/`cmd_ScriptInit` с `control.in: null`.
- [ ] Есть хотя бы одна команда с `role:"address"`-выходом (мост для
      схождения веток), если в языке вообще есть ветвление.
- [ ] `dataTypes[].options[].value` — валидный `0xNN` в верхнем регистре,
      совпадает с реально кодируемым байтом.
- [ ] Типы с `int`-префиксом — только там, где значение действительно
      знаковое.
- [ ] `boilerplate.start`/`.end` не содержат строк из одних `0xNN`-токенов.
- [ ] Ручной прогон: экспорт графа с `if/else` → импорт того же файла →
      граф совпадает со исходным.
